# Playbook сессий FitMan

**Назначение:** единый порядок запуска и завершения рабочих сессий, чтобы не тащить контекст между чатами и не терять решения.

**Связанные документы:**
- [План внедрения логирования и аудита](logging-audit-plan.md)
- [Правила проекта](AGENTS.md)
- `docs/module-status.md` — создаётся в сессии 1a

---

## 1. Модель сессий

| Роль | Пример имени | Что внутри | Можно ли форкать |
| --- | --- | --- | --- |
| Штаб | `00-roadmap` | решения, статус, ссылки; без кода | да, но лучше не надо |
| Работа | `01a-logging`, `01b-audit`, `07-groups` | один вертикальный срез | да, для подзадач |
| Подзадача | `01a-backend`, `01a-frontend` | форк рабочей сессии | нет |
| Ревью | `01a-review` | форк рабочей сессии после кода | нет |
| Handoff | `00-handoff` | короткая выжимка решений для форков | да |

**Источник истины — файлы, а не родительская сессия.** План, матрица модулей и ТЗ должны быть достаточны, чтобы новая сессия стартовала без истории чата.

---

## 2. Именование

```
<номер>-<тема>         01a-logging, 01b-audit, 07-groups
<номер>-<тема>-<часть> 01a-backend, 01a-frontend
<номер>-review         01a-review
```

Номер совпадает с разделом 10 плана. Тема — латиницей, коротко.

---

## 3. Старт сессии

Чек-лист:

1. Создать **новую** сессию (не форк), кроме случаев из раздела 6.
2. Проверить git: ветка, чистый статус, `dart analyze` и тесты до изменений.
3. Прочитать:
   - `docs/logging-audit-plan.md` — раздел 10 и профильные разделы;
   - 1–2 файла ТЗ по модулю из `tz-split`;
   - `docs/module-status.md`, если существует;
   - текущий код модуля.
4. Сформулировать план на 5–7 строк: таблицы, эндпоинты, экраны, тесты, что **не** делаем.
5. Задать вопросы, если есть развилки. Не начинать код с неясным контрактом.
6. Только после этого — реализация.

## 4. Шаблон промпта

### 4.1. Foundation / инфраструктурная сессия

```text
Сессия 1a: Foundation — логирование и обработка ошибок.

Прочитай:
- docs/logging-audit-plan.md (раздел 0, 3.1–3.2, 3.7, 10.1–10.3)
- docs/AGENTS.md
- backend/bin/server.dart, backend/lib/config/app_config.dart

Задача:
1. AppLogger на package:logging (уровни, JSON/текст, файл EFT_YYYY_MM_DD.log).
2. Middleware requestId + accessLog + errorHandler.
3. AppException и контракт ошибки {code, message, requestId}.
4. Убрать e.toString() из ответов.
5. Включить avoid_print, заменить print в backend/lib.
6. Конфиг LOG_LEVEL/LOG_DIR/LOG_FORMAT/LOG_RETENTION_DAYS.

Не делать: audit_log, lesson_events, фронтенд, правки ТЗ.

DoD:
- 5xx логируются с request_id и стеком;
- клиент не видит внутренних деталей;
- в backend/lib нет print();
- dart analyze и тесты проходят.

Сначала покажи план и вопросы, потом код.
```

### 4.2. Модульная сессия

```text
Сессия 07: Группы.

Прочитай:
- docs/logging-audit-plan.md (3.7, 10.1, 10.3)
- docs/tz-split/part-1/09-modul-upravleniya-gruppami.md
- docs/module-status.md
- backend/lib/modules/groups, frontend/lib/modules/groups

Задача: вертикальный срез групп — схема, API, каркас экрана, тесты,
логирование на границах, AppException, аудит изменений.

Не делать: полную бизнес-логику аналитических групп, чат, уведомления.

DoD: CRUD групп и состава работает; аудит пишется в транзакции;
dart analyze и тесты проходят; карточка модуля обновлена.
```

### 4.3. Форк подзадачи

```text
Это форк сессии 01a. Контекст и решения — из родителя.
Задача: только frontend-часть (провайдеры и экран ошибки).
Не менять backend и не трогать ТЗ.
В конце — список изменённых файлов и что осталось.
```

## 5. Финиш сессии

1. `dart analyze` и тесты — без новых ошибок.
2. Коммит(ы) с осмысленным сообщением.
3. Обновить `docs/module-status.md`: схема / API / UI / тесты / лог / аудит.
4. Если принято архитектурное решение — дописать его в план (раздел 0 или профильный).
5. Короткий отчёт в чат:
   - что сделано;
   - что осталось;
   - какие решения приняты;
   - что вынесено в backlog;
   - какая следующая сессия.

Сессия не считается закрытой, если решения остались только в переписке.

## 6. Форки

### Когда можно

- параллельные подзадачи одной сессии: backend и frontend;
- ревью уже написанного кода с полным контекстом;
- эксперимент с двумя вариантами;
- продолжение после паузы, если нужно сохранить детали реализации.

### Когда нельзя

- для последовательных сессий 1a → 1b → модули;
- от длинной «штабной» сессии с историей ТЗ и `.docx`;
- если решение ещё не зафиксировано в файле.

### Правила

1. Форкать **рабочую** сессию, а не штаб.
2. Один модуль — не больше двух параллельных веток.
3. В каждой ветке — свой git-worktree или ветка, чтобы не конфликтовать.
4. После завершения — вручную перенести результат в основную ветку и обновить план.
5. Помнить: форк не синхронизируется с родителем и другими ветками.

---

## 7. Git

- Ветка на сессию: `feature/01a-logging-foundation`, `feature/07-groups`.
- Коммиты: `feat(logging): ...`, `fix(groups): ...`, `chore(db): ...`, `docs(plan): ...`.
- Одна сессия — один PR (или один набор коммитов), чтобы ревью совпадало с планом.
- Не смешивать в одном PR foundation и модуль.
- `.docx` не в git — правки ТЗ фиксируются отдельным решением и перегенерацией.

---

## 8. Контекст

- Читать 1–3 файла ТЗ, а не все 43.
- Не пересказывать ТЗ «своими словами» без запроса — цитировать раздел.
- План и `module-status.md` важнее истории чата.
- Если контекст разросся — закрыть сессию и начать новую с handoff-абзаца.

---

## 9. Типичные ошибки

| Ошибка | Последствие | Как избежать |
| --- | --- | --- |
| Форк длинной штабной сессии | токены на шум, расхождение решений | новая сессия + план |
| Код без зафиксированного контракта ошибок | переделка всех модулей | 1a до костяка |
| Аудит «потом, целиком» | 14 модулей без аудита | аудит в каждой write-сессии |
| Сессия «на весь backend» | не помещается в контекст | один вертикальный срез |
| Решения только в чате | следующая сессия их не знает | писать в план |
| Смешение foundation и фичи | долгий PR, сложное ревью | отдельные сессии |

## 10. Связь с планом
