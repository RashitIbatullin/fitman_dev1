# Шаблон UI каталога FitMan

**Назначение:** единый порядок экранов-каталогов: дашборд → фильтры →
список → карточки. Основа — «Мои услуги»; тот же каркас используется для
каталога оборудования и услуг сотрудника.

Связанные документы: [module-template.md](module-template.md),
[services-tz-draft.md](services-tz-draft.md).

---

## 1. Каркас экрана

```
Scaffold
├── AppBar: название, действия роли
├── floatingActionButton: «+» и/или основная операция
└── body: Column
    ├── плашки показателей
    ├── плашка фильтров
    └── Expanded: список карточек
```

Правила:

- экран — **дашборд, а не голый список**; показатели и фильтры всегда
  видимы, список скроллится отдельно;
- список — `ListView.builder`, а не `Column` с детьми;
- действия, меняющие данные, — в FAB или в меню строки, не в AppBar,
  если их больше одного;
- пустое состояние — на месте списка, с иконкой и коротким текстом.

Пример: [my_services_screen.dart](../frontend/lib/modules/services/screens/my_services_screen.dart).

---

## 2. Плашки показателей

- 3–5 плашек, не больше; каждая отвечает на один вопрос.
- Формат: крупное число + короткая подпись.
- Кликабельная плашка переключает соответствующий фильтр и показывает
  активное состояние (рамка/фон).
- Показатели считаются по **всем** данным экрана, а не по текущей
  отфильтрованной выборке.
- Не дублировать в плашках то, что уже видно в фильтрах.

Для «Моих услуг»:

| Плашка | Смысл |
| --- | --- |
| Всего | все покупки, включая архив |
| Активных | действующие и замороженные |
| Осталось занятий | сумма остатков; `∞`, если есть безлимит |
| В архиве | вручную архивированные |

## 3. Фильтры

- Один механизм фильтрации по разделу. **Нельзя одновременно** делать
  вкладки и комбобокс по одному и тому же признаку: пользователь
  выбирает тип, а вкладка остаётся другой — записи «исчезают».
- Обязательный набор:
  - поиск по названию;
  - комбобокс раздела/типа с обобщёнными значениями;
  - переключатель «Архив».
- В комбобоксе должен быть вариант **«Все»**; значения — те же
  обобщённые категории, что и в бизнес-модели:
  «Тренировки», «Медицина», «Косметология», «Прочие услуги».
- Значение по умолчанию — осмысленное для экрана (для «Моих услуг» —
  «Тренировки»); «Все» доступно, но не обязано быть стартовым.
- Фильтры — локальное состояние экрана; в провайдеры их не тащить.
- При смене фильтра не перезапрашивать данные, если хватает локальной
  фильтрации уже загруженного списка.

## 4. Список

Строка списка отвечает «что это и в каком оно состоянии», но не
заменяет карточку.

Обязательный состав:

- цветная иконка типа (иконка по типу, цвет — по разделу);
- название;
- тип/раздел;
- ключевой показатель: остаток, квота, срок;
- плашка статуса;
- для архивных — дополнительная плашка «Архив».

Запрещено:

- цена/стоимость в списке — она уходит в карточку;
- технический код/ID в списке — это не пользовательское поле;
- редактирование полей прямо в строке;
- дублирование одного и того же статуса двумя плашками.

Статусы и архив — **разные вещи**:

- «Активна», «Исчерпана», «Истекла», «Отменена», «Возвращена» — статусы;
- «Архив» — только результат ручной архивации.

## 5. Действия

### 5.1. Плавающие кнопки

- «+» — создание позиции **каталога** (услуги, оборудования);
- основная операция — отдельная extended-FAB («Оформить услугу»);
- у каждой FAB — свой `heroTag`, иначе несколько FAB в одном экране
  конфликтуют.

### 5.2. Меню строки

Меню (гамбургер) — только у ролей, которым разрешены действия.
Для клиента меню **не показывается вообще**, даже с одним пунктом.

Для «Моих услуг» меню сотрудника:

- **Изменить** — карточка редактирования;
- **Архивировать** — только для завершённых;
- **Деархивировать** — для архивных.

Для каталога услуг сотрудника:

- **Изменить**;
- **Архивировать** — только для снятых с продажи;
- **Деархивировать**.

Активные сущности не архивируются: на бэкенде это `409`, в UI пункт
недоступен. Сначала снимают с продажи/дожидаются завершения.

## 6. Карточки

### 6.1. Просмотр

- Все значимые поля: тип, статус, срок, остаток/квота, стоимость,
  оплата, архив.
- Стоимость и технические детали — здесь, не в списке.
- Кнопка/иконка «Изменить» — только у роли с правами.

### 6.2. Редактирование

- Отдельный экран, не диалог, если полей больше 3–4.
- Цена, срок и остаток оформленной услуги не редактируются: это факт.
- В карточке покупки меняется только **факт оплаты** (статус, источник).
- `isActive` («Доступна для продажи») меняется только в карточке
  **услуги каталога**, не в покупке клиента.
- Архив и `isActive` — независимые состояния.

## 7. Особый случай: каталог у клиента

Один экран может открываться в двух режимах:

| Режим | Что видно | Действия |
| --- | --- | --- |
| Клиент (свой кабинет) | только свои записи | просмотр; меню и FAB скрыты |
| Админ/менеджер (из списка клиентов) | записи выбранного клиента | просмотр, создание, изменение, архивация |

Правила:

- роль определяется по текущему пользователю, а не по факту открытия
  экрана;
- клиент не должен видеть чужие записи: проверка и на фронте, и на
  бэкенде (`403` на чужой `clientId`);
- клиенту не показываем меню действий и FAB создания/продажи, если
  действие ему не разрешено;
- серверная проверка роли обязательна: скрытая кнопка — не защита;
- при открытии сотрудником заголовок и данные — выбранного клиента,
  а действия доступны как сотруднику.

## 8. Данные и обновление

- Список — `FutureProvider`/`AsyncNotifier`, фильтры — локальный
  `State`.
- После создания/изменения/архивации инвалидировать только связанные
  провайдеры, не весь экран.
- После возврата из карточки редактирования — обновить список, если
  карточка вернула `true`.
- Ошибки — `SnackBar` с понятным текстом; пустой список и ошибка —
  разные состояния.

---

## 9. Иконки и визуал

- Иконка — по конкретному типу, цвет — по разделу
  ([service_type_visuals.dart](../frontend/lib/modules/services/utils/service_type_visuals.dart)).
- Один тип — одна иконка; не менять её между списком и карточкой.
- Цветные иконки — белые на цветном фоне, чтобы читались в списке.
- Если нужны PNG/SVG-иллюстрации, их сначала добавляют в `assets`
  и подключают централизованно; не хардкодить пути в экранах.

---

## 10. Частые ошибки

- вкладки + комбобокс по одному признаку;
- `ValueKey(null)` у нескольких соседних дропдаунов — падение
  «Duplicate keys found»;
- цена или код в списке;
- автоматическая архивация по статусу (`expired`/`exhausted`);
- меню действий у клиента;
- архивация активной записи;
- фильтр по конкретному типу при обобщённых разделах;
- пустое состояние без объяснения, почему список пуст.

---

## 11. Чек-лист экрана-каталога

- [ ] дашборд: 3–5 плашек, показатели по всем данным;
- [ ] фильтры: поиск + раздел с «Все» + «Архив»;
- [ ] один механизм фильтрации, без дублирующих вкладок;
- [ ] список: иконка типа, название, тип, остаток/срок, статус;
- [ ] цены и коды в списке отсутствуют;
- [ ] тап по строке открывает карточку просмотра;
- [ ] карточка редактирования отдельная, с валидацией;
- [ ] архив только ручной, причина сохраняется;
- [ ] активные записи не архивируются (UI + API);
- [ ] клиенту меню и FAB не показываются;
- [ ] бэкенд проверяет роль и владельца;
- [ ] после изменений обновляются нужные провайдеры;
- [ ] `dart analyze` без замечаний.
