## 0. Зафиксированные решения (22.11.2026)

| № | Решение | Статус |
| --- | --- | --- |
| 1 | Пакет логирования — `logging` | принято |
| 2 | JSON в проде, текст в dev; файл `EFT_YYYY_MM_DD.log`; в консоль всё, кроме `debug` | принято |
| 3 | Контракт ошибки — `{"error":{"code","message","requestId"}}` | принято |
| 4 | Список ПДн, запрещённых к логированию | принято |

### 0.1. Пакет логирования

Берём `package:logging`, не `logger`.

- `logging` — минимальная зависимость, стандартные `Logger`/`Handler`, легко добавить файловый sink и JSON-форматтер;
- `logger` удобнее «из коробки», но тянет свой формат и настройки, которые придётся обходить ради требований ТЗ;
- `dart:developer` оставляем для frontend, на backend он не даёт файлового sink.

### 0.2. Формат и приёмники

- `LOG_FORMAT=json` в проде, `text` в dev.
- Файл: `$LOG_DIR/EFT_YYYY_MM_DD.log`, по умолчанию `logs/`.
- В файл — всё до уровня `LOG_LEVEL` включительно.
- В консоль — всё, кроме `debug` (требование ТЗ: «сообщение, кроме отладочного, должно выводиться на экран»).
- Поля записи: `ts`, `level`, `logger`, `msg`, `request_id`, `user_id`, `route`, `method`, `status`, `duration_ms`, `entity`, `entity_id`, `error`, `stack`.
- Ретеншн: `LOG_RETENTION_DAYS=30` по умолчанию, для prod — 90.

Конфиг:

```env
LOG_LEVEL=info
LOG_DIR=logs
LOG_FORMAT=json
LOG_RETENTION_DAYS=30
```

### 0.3. Контракт ошибки

```json
{
  "error": {
    "code": "LESSON_CONFLICT",
    "message": "Занятие пересекается по времени",
    "requestId": "0f3c9a2e-..."
  }
}
```

- HTTP-статус остаётся отдельно (`400`, `401`, `403`, `404`, `409`, `500`);
- `code` — стабильный машинный код, не меняется при правках текста;
- `message` — безопасный текст для пользователя, без SQL, стека и имён таблиц;
- `requestId` — тот же, что в логе и заголовке `X-Request-ID`.

Базовые коды: `VALIDATION_ERROR`, `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`, `INTERNAL_ERROR`. Доменные коды (`LESSON_CONFLICT`, `GROUP_FULL`, `ROOM_BUSY`) добавляются по мере модулей.

### 0.4. ПДн и секреты: запрещено логировать

- телефон, email, ФИО, дата рождения, адрес;
- паспортные и медицинские данные, антропометрия, биоимпеданс;
- пароли, `password_hash`, JWT/refresh-токены, SMS-коды;
- заголовки `Authorization`, cookies;
- тела запросов и ответов целиком;
- параметры SQL-запросов;
- фото и ссылки на файлы с ПДн.

Разрешено: `user_id`, `entity_id`, `request_id`, `route`, `method`, `status`, `duration_ms`, `role`, `source`.

Правило маскирования: если поле всё же нужно для диагностики — только `***` или необратимый хеш, не исходное значение.

## 1. Контекст

Сейчас в проекте нет системы логирования и нет аудита:

- 318 вызовов `print()` в 50 Dart-файлах, ноль `debugPrint()`/`developer.log()`;
- в `backend/pubspec.yaml` и `frontend/pubspec.yaml` нет пакета логирования;
- `avoid_print` отключён в `analysis_options.yaml`;
- `audit_log` отсутствует и в Dart-коде, и в `database/*.sql`;
- внутренние ошибки уходят клиенту через `e.toString()`;
- нет `request_id`, нет корреляции запросов и записей БД;
- нет RLS и контекста актора в БД, `Database` — синглтон с одним `Connection`.

Цель плана — получить три независимых, но связанных слоя:

| Слой | Назначение | Хранение | Срок |
| --- | --- | --- | --- |
| Технический лог | диагностика, инциденты, тайминги | stdout + файл `EFT_YYYY_MM_DD.log` | 30–90 дней |
| Аудит | кто/что/когда изменил, комплаенс | PostgreSQL `audit_log` | 36 месяцев |
| Доменная история | отмена/перенос/смена зала для UI и уведомлений | PostgreSQL `lesson_events` | бессрочно, по политике |

---

## 2. Принципы

1. **Один источник истины на слой.** Технический лог не является аудитом; аудит не используется для диагностики.
2. **Логирование на границе.** Логируем в middleware/сервисе, а не в каждом `catch` репозитория. Ошибку логируем один раз.
3. **Никаких ПДн и секретов.** Телефоны, email, пароли, токены, тела запросов и SQL-параметры — не попадают в лог. Маскирование централизованное.
4. **Клиенту — безопасный ответ.** Внутренние детали (SQL, стек, текст исключения) остаются в логе; клиент получает код, сообщение и `requestId`.
5. **Аудит в транзакции.** Запись аудита коммитится и откатывается вместе с бизнес-изменением.
6. **Явный актор.** `changed_by`, `actor_role`, `request_id`, `source` передаются в аудит явно, а не вычисляются из общего соединения.
7. **Совместимость с ТЗ.** Уровни, имя суточного файла, срок аудита и доступ только администратору — берём из ТЗ, не изобретаем.

## 3. Целевая архитектура

### 3.1. Backend: pipeline запроса

```
requestId → accessLog → errorHandler → cors/helmet → auth → router
```

- `requestId`: принимает `X-Request-ID` или генерирует UUID, кладёт в `request.context`, возвращает в ответе.
- `accessLog`: одна запись на запрос — `method`, `path`, `status`, `duration_ms`, `request_id`, `user_id`, `route`.
- `errorHandler`: ловит необработанные исключения, логирует стек с `request_id`, отдаёт безопасный JSON.

Контракт ошибки:

```json
{"error":{"code":"LESSON_CONFLICT","message":"Занятие пересекается по времени","requestId":"..."}}
```

### 3.2. Backend: логгер

- пакет `logging` + собственная обёртка `AppLogger`;
- уровни `debug/info/warning/error`, уровень из `LOG_LEVEL`;
- JSON-формат в проде, читаемый — в dev;
- sinks: stdout + файл `logs/EFT_YYYY_MM_DD.log`;
- поля: `ts`, `level`, `logger`, `msg`, `request_id`, `user_id`, `route`, `entity`, `entity_id`, `duration_ms`, `error`, `stack`;
- ретеншн `LOG_RETENTION_DAYS`, ротация по дню и размеру.

### 3.3. Аудит в PostgreSQL

```sql
CREATE TABLE audit_log (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  table_name   text NOT NULL,
  row_pk       uuid NOT NULL,
  action       text NOT NULL,          -- INSERT/UPDATE/DELETE/ARCHIVE/RESTORE
  changed_at   timestamptz NOT NULL DEFAULT now(),
  changed_by   uuid REFERENCES users(id),
  actor_role   text,
  request_id   uuid,
  source       text NOT NULL DEFAULT 'api', -- api/offline/system/job
  reason       text,
  old_values   jsonb,
  new_values   jsonb
);
```

- запись через `AuditService.record(...)` в той же транзакции, что и изменение;
- актор и `request_id` передаются из `request.context` через сервисный слой;
- триггерный вариант — только после появления пула соединений и `SET LOCAL app.user_id/app.request_id` на транзакцию;
- неизменяемость: запрет `UPDATE/DELETE`, отдельная роль, guard-триггер;
- индексы: `(table_name, row_pk, changed_at DESC)`, `(changed_at)`;
- партиционирование по месяцам и ретеншн 36 месяцев — после стабилизации схемы;
- API и экран истории — только для роли `admin`.

### 3.4. Доменная история занятий

```sql
CREATE TABLE lesson_events (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  lesson_id    uuid NOT NULL REFERENCES lessons(id),
  event_type   text NOT NULL,          -- cancel/reschedule/room_change/restore
  old_start_at timestamptz,
  new_start_at timestamptz,
  old_room_id  uuid REFERENCES rooms(id),
  new_room_id  uuid REFERENCES rooms(id),
  reason       text,
  changed_by   uuid REFERENCES users(id),
  changed_at   timestamptz NOT NULL DEFAULT now(),
  notified_at  timestamptz,
  request_id   uuid
);
```

- пишется в сервисах отмены/переноса/смены зала;
- используется карточкой занятия, отчётом «процент отменённых/перенесённых» и уведомлениями;
- `audit_log` остаётся для администратора и разбора, `lesson_events` — для продукта.

### 3.5. Frontend

- `AppLogger` на `dart:developer log()` с уровнями и контекстом;
- глобальные перехватчики: `runZonedGuarded`, `FlutterError.onError`, `PlatformDispatcher.instance.onError`;
- `ProviderObserver` пишет через логгер;
- `ApiException(statusCode, code, message, requestId)` вместо `Exception(string)`;
- пользователю — дружелюбное сообщение, в лог — статус, код и `requestId`;
- токены и ПДн не логируются.

### 3.6. Эксплуатация

- каталог `LOG_DIR`, файлы `EFT_YYYY_MM_DD.log`, ретеншн и контроль диска;
- алерты: рост 5xx, ошибки БД, сбой записи аудита, всплеск 401;
- `logRequests()` Shelf остаётся транспортом, но не заменяет прикладной лог;
- runbook: где искать лог, как сопоставить `request_id`, как выгрузить аудит.

### 3.7. Что делать до костяка модулей, а что после

Полный аудит логично отложить до появления костяка всех модулей: иначе его модель придётся переделывать под ещё не устоявшуюся схему. Но четыре вещи дешевле сделать **до** костяка, иначе они превратятся в массовый рефакторинг всех модулей.

**До костяка (3–5 дней):**

1. `AppLogger` + запрет `print()` — иначе каждый новый модуль добавит ещё десятки `print`.
2. `request_id` и access-log — middleware прозрачен, но логи без корреляции бесполезны.
3. Контракт ошибок и центральный `errorHandler` — фронтенд сразу строится под `{code, message, requestId}`, а не под `{error: string}`.
4. Конвенция передачи актора: `actorId`, `actorRole`, `requestId` в сигнатурах сервисов/репозиториев. Если модули напишут без неё, аудит потом потребует правок в каждом write-path.
5. Baseline миграций (даже если инструмент простой) — иначе `audit_log` и новые таблицы добавятся в ручные `database/*.sql` и схема разъедется.
6. Шаблон модуля: `controller → service → repository`, ошибки через `AppException`, логирование на границе, актор в параметрах.

**После костяка (основной объём):**

- покрытие `audit_log`, триггеры/сервисный аудит, партиции и ретеншн;
- `lesson_events` и история отмен/переносов;
- админский экран аудита;
- frontend crash-reporting и сквозной `requestId`;
- алерты, дашборды, runbook;
- нормативные правки ТЗ.

Такой порядок даёт совместимость: костяк сразу пишется с логированием и актором, а тяжёлая часть аудита не блокирует разработку модулей.

## 4. Этапы

Оценки — для одного разработчика, без учёта согласований.

> Этапы 1–2 — это foundation из п. 3.7: их лучше сделать до костяка модулей. Этапы 3–6 — после костяка, когда схема и модули устоялись.

### Этап 0. Подготовка (0,5–1 день)

- зафиксировать политику ПДн: что логируем, что маскируем, где храним;
- согласовать список сущностей для аудита в первой волне: `users`, `training_groups`, `rooms`, `lessons`, `equipment_items`, `equipment_maintenance_history`;
- согласовать контракт ошибки и формат `request_id`;
- определить ответственного за эксплуатацию логов.

**Результат:** решения зафиксированы в этом файле или отдельном ADR.

### Этап 1. Технический лог backend (2–3 дня)

- добавить зависимость и `AppLogger`;
- JSON-формат, уровни, файловый sink, конфиг из `.env`;
- заменить `print()` в `backend/lib` (кроме CLI-скриптов сидирования);
- включить `avoid_print`, для `bin/seed.dart` — локальный ignore;
- тесты: уровень, формат, ротация, маскирование.

**Готово, когда:** в `backend/lib` нет `print()`; файл `EFT_YYYY_MM_DD.log` создаётся; уровень меняется через `.env`.

### Этап 2. Request context и ошибки (2–3 дня)

- middleware `requestId`, `accessLog`, `errorHandler`;
- иерархия `AppException` и коды ошибок;
- убрать `e.toString()` из ответов;
- единый формат ошибки, совместимый с фронтендом;
- тесты: 500 не раскрывает детали, `request_id` есть в ответе и логе.

**Готово, когда:** любой 5xx имеет `request_id`, в ответе нет внутренних деталей, в логе есть стек и контекст.

### Этап 3. Аудит БД (4–5 дней)

- миграция `audit_log` + индексы + guard-триггер;
- `AuditService.record(...)` с транзакцией и явным актором;
- покрыть первую волну сущностей;
- API истории для администратора;
- тесты: commit → запись есть; rollback → записи нет; актор корректен.

**Готово, когда:** изменения первой волны попадают в аудит атомарно; `UPDATE/DELETE` по `audit_log` запрещены; история доступна администратору.

### Этап 4. Доменная история занятий (3–4 дня)

- миграция `lesson_events`;
- запись событий в отмене/переносе/смене зала;
- связь с уведомлениями (`notified_at`, outbox);
- вкладка истории в карточке занятия;
- отчёт «процент отменённых/перенесённых» — на `lesson_events`.

**Готово, когда:** отмена, перенос и смена зала видны в карточке; уведомление ссылается на событие; отчёт не зависит от текущего `complete`.

### Этап 5. Frontend (2–3 дня)

- `AppLogger`, глобальные перехватчики;
- `ProviderObserver` через логгер;
- `ApiException` и дружелюбные сообщения;
- тесты на отсутствие токенов/ПДн в логах.

**Готово, когда:** необработанные ошибки логируются; пользователь не видит текст сервера; статус-код доступен в обработчике.

### Этап 6. Эксплуатация и hardening (2 дня)

- ретеншн, ротация, контроль диска;
- алерты и дашборд;
- runbook;
- проверка доступа к аудиту.

**Готово, когда:** логи не растут бесконечно; есть алерты; инцидент разбирается по `request_id`.

### Этап 7. Технический долг БД (1–2 недели, отдельный трек)

- инструмент миграций вместо ручных `database/*.sql`;
- пул соединений и транзакция на запрос;
- RLS и `SET LOCAL app.user_id`;
- при необходимости — перенос аудита на триггеры;
- сведение `training_group_member_movements`/`maintenance_status_history` к единой модели и именам из ТЗ.

## 5. Порядок и зависимости

Базовый вариант — сначала костяк модулей, затем тяжёлый аудит. Но foundation из п. 3.7 (логгер, `request_id`, контракт ошибок, актор, миграции, шаблон модуля) делается **до** костяка.

```
Foundation (3–5 дней) → костяк модулей → аудит/lesson_events → frontend hardening → эксплуатация
```

- Этап 5 нельзя начинать до фиксации контракта ошибок (Этап 2).
- Этап 3 можно делать без Этапа 4; `lesson_events` — отдельная ценность.
- Этап 7 обязателен, если аудит должен быть именно триггерным по ТЗ; при сервисном аудите его можно отложить.

## 6. Критерии готовности (общие)

- 0 `print()` в production-коде; `avoid_print` включён.
- 4 уровня, уровень из конфига, суточный файл `EFT_YYYY_MM_DD.log`, ретеншн.
- 100% 5xx логируются с `request_id`, стеком и контекстом; клиент не видит внутренних деталей.
- Аудит пишется в транзакции, неизменяем, хранится 36 месяцев, доступен только администратору.
- Отмена/перенос/смена зала занятия отражены в `lesson_events` и видны в UI.
- В логах нет телефонов, email, паролей, токенов и тел запросов.
- Есть runbook и алерты.

## 7. Риски

| Риск | Влияние | Мера |
| --- | --- | --- |
| Массовая замена `print()` теряет контекст | среднее | менять по модулям, сохранять поля `entity`/`entity_id` |
| Аудит в транзакции при одном соединении | высокое | сначала пул/транзакция на запрос или сервисный аудит без триггеров |
| Нет миграций, схема расходится | высокое | ввести миграции до `audit_log` |
| Смена контракта ошибок ломает фронтенд | среднее | версионировать ответ, обновить `BaseApiService` одновременно |
| ПДн уже попали в старые логи | высокое | ротация и удаление старых файлов, политика маскирования |
| Рост `audit_log` | среднее | партиции по месяцам, ретеншн, архив |
| Дублирование истории | среднее | один источник истины, остальные — проекции |

## 8. Что добавить в ТЗ

План — это roadmap, а не требование. В ТЗ имеет смысл внести только нормативные пункты:

1. **`request_id`** — обязателен для каждого запроса и каждой записи аудита.
2. **Контракт ошибки** — код, сообщение, `requestId`; запрет на внутренние детали в ответе.
3. **ПДн** — перечень полей, запрещённых к логированию, и правило маскирования.
4. **Аудит** — `request_id`, `reason`, `actor_role`, `source`; запись в транзакции изменения; неизменяемость.
5. **Доменные события занятий** — `lesson_events` для отмены/переноса/смены зала.
6. **Технические логи** — уровень из настроек, `EFT_YYYY_MM_DD`, ретеншн.
7. **Доступ** — аудит только администратору; история занятия — тренеру/менеджеру в рамках их групп.

Пункты 1–7 меняют `.docx`-исходники, поэтому вносятся отдельным решением с перегенерацией `tz-split`.

## 10. Разбиение на сессии

Идея: одна сессия — один вертикальный срез (схема → API → UI-каркас → тесты), а не «весь backend» или «весь frontend». Так каждая сессия помещается в контекст, а архитектура проверяется на реальном модуле.

Сессия 1 делится на две: foundation и аудит-каркас — это разные по смыслу работы, и вместе они не помещаются в один заход.

### 10.1. Последовательность

| № | Сессия | Содержание | Выход | Оценка |
| --- | --- | --- | --- | --- |
| **1a** | Foundation: лог и ошибки | `AppLogger`, `request_id`, access-log, `AppException`, `errorHandler`, `avoid_print`, конфиг уровней | любой 5xx логируется с `request_id`; клиент не видит внутренностей | 2 дня |
| **1b** | Foundation: аудит и шаблон | миграции, `audit_log`, `AuditService`, конвенция актора, шаблон модуля, первый аудит на `rooms` | шаблонный модуль пишет аудит в транзакции | 2–3 дня |
| **2** | Пользователи и доступ | `users`, `roles`, `user_roles`, профили, `user_settings`, auth | вертикальный срез users + аудит + логи | 2 дня |
| **3** | Справочники | цели, уровни, виды активности, типы тела, типы упражнений, BMR-формулы | API справочников + экраны-заглушки | 1–2 дня |
| **4** | Инфраструктура | здания, помещения, расписания помещений | CRUD + аудит помещений | 1–2 дня |
| **5** | Оборудование и ТО | типы, экземпляры, брони, заявки ТО, статусы, фото | вертикальный срез оборудования и ТО | 2–3 дня |

| **7** | Группы | типы групп, группы, состав, перемещения, слоты, замены | группы + история перемещений + аудит | 2 дня |
| **8** | Расписание и занятия | расписания, повторения, исключения, уведомления, `lessons`, `lesson_events` | календарь + отмена/перенос/смена зала | 3 дня |
| **9** | Клиенты и измерения | профили, антропометрия, биоимпеданс, калории, дашборд | клиентский срез + аудит измерений | 3 дня |

| **11** | Отчётность | отчёты по клиентам, занятиям, загрузке, финансам | API отчётов + экран-заглушка | 2 дня |
| **12** | Онбординг и сайт | лиды, приглашения, активация, заявки с сайта | воронка лидов | 1–2 дня |
| **13** | Офлайн и синхронизация | кэш, очередь операций, конфликты, `client_event_id` | каркас offline-first | 2–3 дня |
| **14** | Аудит: окончание | админский экран аудита, история занятия, партиции, ретеншн, отчётность по событиям, правки ТЗ, runbook | аудит закрыт сквозным сценарием | 3–4 дня |

**Итого:** ~30–38 рабочих дней, то есть 6–8 недель с учётом интеграции и тестов. Оценки грубые, без согласований и приёмки.

### 10.2. Почему такой порядок

- **1a → 1b:** сначала лог и ошибки, потом аудит: `AuditService` уже сможет писать `request_id`.
- **2 → 3:** пользователи и справочники — фундамент для всех остальных FK.
- **4 → 5:** помещения и оборудование нужны группам и расписанию.
- **6 → 7 → 8:** планы → группы → занятия; занятие ссылается на план, группу, зал и тренера.
- **9:** клиентские измерения зависят от пользователей, планов и занятий.
- **10 → 11:** чат и уведомления зависят от расписания; отчётность — от всех данных.
- **12 → 13:** онбординг и офлайн можно делать после основного ядра.
- **14:** UI и политика аудита — когда все сущности уже пишут аудит.

### 10.3. Что делать в каждой сессии

**На входе:**
- прочитать `docs/logging-audit-plan.md` (этот файл), ТЗ по модулю (1–2 файла из `tz-split`), текущий код модуля;
- зафиксировать scope: какие таблицы, эндпоинты, экраны;
- проверить, что foundation уже работает (лог, `request_id`, ошибки, актор).

**На выходе:**
- миграция и схема;
- репозиторий + сервис + контроллер по шаблону;
- фронтенд: провайдер + экран-каркас (не обязательно полный UI);
- логи на границах, ошибки через `AppException`, актор в write-path;
- аудит для сущностей модуля (если это write-модуль);
- тесты на happy path + один отказ;
- `dart analyze` и прогон тестов;
- обновлённая карточка модуля (см. 10.4).

**Правила:**
- одна сессия — один модуль; если не помещается, делить на «backend» и «frontend», а не растягивать;
- найденные архитектурные проблемы не чинить «попутно» — в backlog;
- не смешивать foundation и фичи;
- после сессии — короткий отчёт: что сделано, что осталось, какие решения приняты.

### 10.5. Что считать «костяком»

В этом плане «костяк» — не полная бизнес-логика, а **работающий вертикальный срез**: схема, CRUD-API, каркас экрана, обработка ошибок, логи, аудит, тесты. Сложные правила (конфликты расписания, прогрессии планов, аналитические группы) — отдельные follow-up сессии после прохождения всех модулей.
