# Функциональные требования / Архивация и восстановление записей

*Часть 2 | источник: Требования ТЗ фитнес-тренинг часть 2.docx | [индекс](../INDEX.md)*

  - В каждой таблице обязательно присутствуют два служебных поля:
archived_at timestamp with time zone NULL – дата/время архивации;

archived_by uuid NULL – ссылка на users(id), кто архивировал.
NULL в обоих полях означает «запись активна».

  - Архивация выполняется командой ArchiveEntityCommand (паттерн Command), которая:
проверяет право «Архивировать» у текущей роли;

заполняет archived_at = now(), archived_by = current_user_id;

пишет запись в audit_log (действие = ‘ARCHIVE’).

  - Восстановление – командой RestoreEntityCommand, которая:
сбрасывает archived_at и archived_by в NULL;

пишет в audit_log действие ‘RESTORE’.

  - На всех таблицах создаётся RLS-политика (или эквивалентный механизм БД):
```sql
USING (archived_at IS NULL)
Политика действует для ролей «Клиент», «Инструктор», «Тренер», «Менеджер».
Роль «Администратор» видит записи без ограничений.
Списочные формы по умолчанию не выводят архивные строки. Чек-бокс «Показать архивные» добавляет условие archived_at IS NOT NULL.
Экспорт/отчёты/API-методы, не предназначенные для администратора, автоматически фильтруют archived_at IS NULL.
Физическое удаление (DELETE) запрещено; используется только логическое удаление через архивацию.
```
